# EPAM Round 2 – Java Full Stack Interview Questions and Answers

**Focus:** Java, Streams, Collections, Mockito/JUnit, SQL, Spring, design patterns, AI/agentic workflows, and coding.

> These are concise, interview-ready answers. Where behaviour depends on the implementation or Java version, that is noted.

## 1. Synchronous vs. Asynchronous

**Synchronous:** The caller waits for an operation to finish before continuing.

```java
String user = userService.getUser(); // waits for the method to return
System.out.println(user);
```

**Asynchronous:** The caller can continue while the operation completes separately, with the result handled later.

```java
CompletableFuture.supplyAsync(() -> userService.getUser())
    .thenAccept(System.out::println);
```

**Key point:** Synchronous/asynchronous describes execution and waiting; it does not by itself determine thread safety.

## 2. Which is thread-safe: synchronous or concurrent execution?

Neither is automatically thread-safe. **Thread safety depends on shared state and synchronization.** Synchronous code can still have race conditions if multiple threads call it. Concurrent code can be thread-safe when it uses suitable coordination, immutable data, locks, or concurrent collections.

For example, `ConcurrentHashMap` supports safe concurrent access to its entries. A plain `HashMap` does not support unsynchronized concurrent modification.

## 3. Inheritance vs. Composition

- **Inheritance (“is-a”):** A subclass extends a parent class and inherits its behaviour.
- **Composition (“has-a”):** A class contains or uses another object to delegate work.

```java
class Animal {
    void eat() { System.out.println("Eating"); }
}
class Dog extends Animal { } // Dog is an Animal

class Engine {
    void start() { System.out.println("Engine started"); }
}
class Car {
    private final Engine engine = new Engine(); // Car has an Engine
    void start() { engine.start(); }
}
```

**Interview answer:** Prefer composition when it gives more flexibility and lower coupling. Use inheritance when there is a genuine substitutable “is-a” relationship.

## 4. Try-with-resources

Try-with-resources automatically closes resources that implement `AutoCloseable`, even when an exception occurs.

```java
try (BufferedReader reader = Files.newBufferedReader(Path.of("input.txt"))) {
    System.out.println(reader.readLine());
} catch (IOException e) {
    e.printStackTrace();
}
```

The resource is closed automatically. If both the body and closing operation throw exceptions, the body exception is primary and the closing exception is generally suppressed.

## 5. Shallow copy vs. Deep copy

- **Shallow copy:** Copies the outer object, but referenced nested objects are shared.
- **Deep copy:** Copies the outer object and the nested mutable objects that need independent state.

```java
class Address {
    String city;
    Address(String city) { this.city = city; }
}
class Person {
    String name;
    Address address;
    Person(String name, Address address) {
        this.name = name;
        this.address = address;
    }
}

// Shallow copy
Person original = new Person("Priya", new Address("Chennai"));
Person shallow = new Person(original.name, original.address);

// Deep copy for this simple model
Person deep = new Person(original.name, new Address(original.address.city));

shallow.address.city = "Pune";
System.out.println(original.address.city); // Pune: nested object is shared

deep.address.city = "Mumbai";
System.out.println(original.address.city); // Still Pune: deep copy is independent
```

Strings are immutable, but mutable nested objects such as `Address` are the important distinction.

## 6. A class has two fields: which copy is shallow or deep, and what changes in the original?

Suppose `Person` has `name` and `Address address`.

- If the copy gets the **same `Address` reference**, changing `copy.address.city` also changes what `original.address.city` reads. This is shallow copying.
- If the copy gets a **new `Address` object**, changing its city does not affect the original. This is deep copying for that nested object.
- Assigning a new value to `copy.name` does not change `original.name`; the fields belong to separate `Person` objects. A `String` value itself is immutable.

## 7. Lazy evaluation in Java Streams

Intermediate stream operations such as `filter`, `map`, and `sorted` are generally lazy: they do not execute until a terminal operation is invoked.

```java
List<Integer> result = List.of(1, 2, 3, 4).stream()
    .filter(n -> {
        System.out.println("Checking " + n);
        return n % 2 == 0;
    })
    .toList(); // terminal operation triggers processing
```

**Benefit:** Streams can avoid unnecessary work and can short-circuit operations such as `findFirst()` and `anyMatch()`.

## 8. Parallel stream vs. sequential stream

- **Sequential:** Processes elements in one stream pipeline without parallel splitting.
- **Parallel:** Splits work across multiple tasks/threads, usually using the common `ForkJoinPool`.

```java
numbers.stream().map(this::calculate).toList();         // sequential
numbers.parallelStream().map(this::calculate).toList(); // parallel
```

Parallel streams can help with large workloads that are CPU-intensive, independent, and sufficiently costly per element. They may be slower for small lists, cheap operations, blocking I/O, or pipelines requiring shared mutable state. Encounter order is not necessarily preserved by every operation; `forEachOrdered` preserves encounter order but can reduce parallel performance.

## 9. I have 100,000 elements. Which stream should I use?

Do not choose based on element count alone. Start with a sequential stream and benchmark realistic data. Consider a parallel stream if each element has enough independent CPU work and the cost of splitting/combining is worthwhile. Avoid shared mutable state and be careful with ordering, thread-safety, and blocking I/O.

```java
long count = numbers.stream()
    .filter(this::isEligible)
    .count();
```

Change to `parallelStream()` only after measuring and confirming that it improves performance for the real workload.

## 10. Can a Java Stream be reused multiple times?

No. A stream is single-use. After a terminal operation, it is consumed; trying to use it again throws `IllegalStateException`.

```java
List<String> names = List.of("Ana", "Bob");
Stream<String> stream = names.stream();

long count = stream.count();
// stream.forEach(System.out::println); // IllegalStateException
```

Create a new stream from the source for each pipeline:

```java
long count = names.stream().count();
names.stream().forEach(System.out::println);
```

For repeated processing, a `Supplier<Stream<T>>` can create a fresh stream each time.

## 11. `peek()` vs. `map()` in Java Streams

- **`map()`** transforms each element and produces a stream of transformed values.
- **`peek()`** performs an action on elements as they pass through, commonly for debugging. It should not be used to transform data or rely on side effects.

```java
List<String> result = List.of("java", "spring").stream()
    .map(String::toUpperCase)
    .toList(); // [JAVA, SPRING]

List<String> debug = List.of("java", "spring").stream()
    .peek(value -> System.out.println("Before: " + value))
    .toList();
```

`peek()` runs only as elements are consumed; optimizations or short-circuiting can mean not every element is observed.

## 12. Fail-fast vs. fail-safe iterators

- **Fail-fast:** Common non-concurrent collection iterators (for example, `ArrayList`) may throw `ConcurrentModificationException` if the collection is structurally modified during iteration outside the iterator's permitted operations. This is best-effort bug detection, not a thread-safety guarantee.
- **“Fail-safe”:** Informal term, not an official Java API category. Concurrent or snapshot-based iterators may tolerate concurrent modification. For example, `CopyOnWriteArrayList` iterators traverse a snapshot; `ConcurrentHashMap` iterators are weakly consistent.

## 13. Why doesn't a fail-safe iterator throw an exception?

Because its iteration model is designed to tolerate concurrent changes, rather than detect and reject every modification. For example, `CopyOnWriteArrayList` iterates over a snapshot of the array as it existed when the iterator was created. Changes made afterward do not appear in that iterator's snapshot. `ConcurrentHashMap` iterators are weakly consistent and may reflect some updates, but do not provide a fixed snapshot.

## 14. How does Java handle a null key in Map implementations?

- `HashMap`: allows one `null` key and multiple `null` values.
- `LinkedHashMap`: allows a `null` key.
- `Hashtable`: does not allow null keys or values.
- `ConcurrentHashMap`: does not allow null keys or values.
- `TreeMap`: null-key support depends on ordering; with natural ordering, a null key is not accepted. A custom comparator may define how null is handled.

Always check the particular implementation's contract.

## 15. Can `TreeSet` store null?

With natural ordering, `TreeSet` does not accept `null` in modern Java implementations because it cannot compare null with ordinary elements; adding it generally throws `NullPointerException`. A `TreeSet` constructed with a comparator that explicitly supports null can store it.

```java
Set<String> values = new TreeSet<>(Comparator.nullsFirst(String::compareTo));
values.add(null);
values.add("Java");
```

## 16. What if the first element added to a `TreeSet` is null?

With the default natural ordering:

```java
Set<String> values = new TreeSet<>();
values.add(null); // NullPointerException
```

The first insertion still requires the set to establish ordering, so it fails. Use a comparator that explicitly handles null if null must be supported.

## 17. JUnit, Mockito `@Mock`, and `@Spy`

- **JUnit** is a testing framework used to write and run unit tests. JUnit 5 uses annotations such as `@Test` and assertions such as `assertEquals`.
- **`@Mock`** creates a mock object. Methods return configured values or Mockito defaults; real method bodies are not called by default.
- **`@Spy`** wraps a real object, so real methods are called by default unless stubbed.
- **`@InjectMocks`** asks Mockito to create the class under test and inject mocks/spies into it where possible.

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock OrderRepository repository;
    @InjectMocks OrderService service;

    @Test
    void returnsOrder() {
        when(repository.findById(1L)).thenReturn(Optional.of(new Order()));
        assertTrue(service.getOrder(1L).isPresent());
        verify(repository).findById(1L);
    }
}
```

## 18. Mockito: real methods in `@Mock` vs. `@Spy`

`@Mock`: real methods are not executed by default; stub them using `when(...).thenReturn(...)` or `doReturn(...).when(...)`.

`@Spy`: real methods execute by default. When stubbing a spy, `when(spy.method())` can call the real method during setup. To avoid that, use:

```java
doReturn("mocked").when(spy).getValue();
```

Use a spy when you specifically need real behaviour for some methods and controlled behaviour for others. Prefer mocks for isolated unit tests when practical.

## 19–20. SQL sorting (`ORDER BY`)

Use `ORDER BY` to sort query results. `ASC` is ascending and is the default; `DESC` is descending. Add more columns to define tie-breaking order.

```sql
SELECT employee_id, name, salary
FROM employees
ORDER BY salary DESC, name ASC;
```

For highest-paid employees, use `ORDER BY salary DESC`. SQL result order is not guaranteed unless an `ORDER BY` clause is specified. Null ordering can vary by database; use `NULLS FIRST`/`NULLS LAST` where supported or an explicit expression for portability.

## 21. SQL normalisation

Normalisation structures relational tables to reduce duplicated data and update anomalies.

- **1NF:** Each field contains an atomic value; no repeating groups.
- **2NF:** In 1NF, and every non-key attribute depends on the whole candidate key (no partial dependency on part of a composite key).
- **3NF:** In 2NF, and no inappropriate transitive dependency of non-key attributes on a key.
- **BCNF:** Every determinant is a candidate key.

Example: Instead of repeating a department name for every employee, store department details in a `Department` table and reference it from `Employee` with a foreign key. Normalisation improves consistency; deliberate denormalisation may be used for measured performance needs.

## 22. What is the Spring ApplicationContext?

`ApplicationContext` is Spring's central IoC container. It creates and manages beans, injects dependencies, supports bean lifecycle callbacks, configuration, events, internationalisation, and integration with Spring features.

```java
ApplicationContext context =
    new AnnotationConfigApplicationContext(AppConfig.class);
MyService service = context.getBean(MyService.class);
```

In Spring Boot, the application context is typically created automatically during startup.

## 23. `BeanFactory` vs. `ApplicationContext`

- **`BeanFactory`:** Core IoC container; provides bean creation and dependency injection.
- **`ApplicationContext`:** Extends `BeanFactory` and adds features such as application events, message-source support, and easier integration with enterprise/application infrastructure.

For most Spring Boot applications, `ApplicationContext` is the normal choice.

## 24. What is a circular dependency in Spring?

A circular dependency occurs when beans depend on each other, directly or indirectly.

Example: `A` requires `B`, while `B` requires `A`. Constructor injection usually causes startup failure because neither bean can be constructed first. Some setter/field-injection cycles may be resolvable in certain configurations, but relying on that is fragile; Spring Boot commonly disallows circular references by default.

## 25. How do you avoid circular dependencies in Spring?

1. Refactor responsibilities so the beans do not depend on each other.
2. Extract shared behaviour into a third service used by both.
3. Introduce events or callbacks where appropriate to reduce direct coupling.
4. If a dependency is genuinely optional or deferred, consider `@Lazy` or `ObjectProvider` as a tactical workaround—not as the first design choice.

**Interview answer:** I first examine the design and break the cycle instead of enabling circular references.

## 26. REST principles

REST (Representational State Transfer) is an architectural style for network APIs. Key principles commonly expected in interviews:

- Client-server separation.
- Stateless requests: each request carries the information needed to process it.
- Cacheability where appropriate.
- Uniform interface using resources and standard HTTP methods.
- Layered system.
- Optional code-on-demand.

Typical HTTP method usage: `GET` reads, `POST` creates or triggers processing, `PUT` replaces, `PATCH` partially updates, and `DELETE` removes. Use meaningful status codes, validation, and consistent error responses.

## 27. What is `DispatcherServlet` in Spring MVC?

`DispatcherServlet` is Spring MVC's front controller. It receives incoming HTTP requests and coordinates request mapping, handler execution, argument resolution, message conversion, exception handling, and response rendering.

Typical flow: request → `DispatcherServlet` → controller → service → repository/database → response. For a REST controller, an `HttpMessageConverter` commonly serializes the returned object to JSON.

## 28. `@Transactional`

`@Transactional` defines a transaction boundary. Spring typically uses AOP proxies and a transaction manager to begin, commit, or roll back a transaction.

```java
@Service
class TransferService {
    @Transactional
    public void transfer() {
        // debit account
        // credit account
    }
}
```

Important details:
- By default, unchecked exceptions (`RuntimeException` and `Error`) trigger rollback; checked exceptions do not unless configured.
- In proxy-based mode, self-invocation (one method calling another method on the same instance) may bypass the proxy and therefore the transaction advice.
- Keep transactions appropriately scoped; avoid long-running external calls inside database transactions where possible.
- A transaction annotation does not automatically make a multi-service distributed workflow one atomic transaction.

## 29. `@Profile` in Spring Boot

`@Profile` registers a bean or configuration only when the specified profile is active.

```java
@Configuration
@Profile("dev")
class DevConfig {
    // development-specific beans
}
```

Activate a profile using configuration such as `spring.profiles.active=dev`, an environment variable, or a deployment configuration. Profiles help separate development, test, and production configuration; do not commit secrets in profile files.

## 30. Factory design pattern

The Factory pattern centralises object creation so client code does not need to know the concrete class being instantiated.

```java
interface Notification {
    void send(String message);
}
class EmailNotification implements Notification {
    public void send(String message) { System.out.println("Email: " + message); }
}
class SmsNotification implements Notification {
    public void send(String message) { System.out.println("SMS: " + message); }
}
class NotificationFactory {
    static Notification create(String type) {
        return switch (type.toLowerCase()) {
            case "email" -> new EmailNotification();
            case "sms" -> new SmsNotification();
            default -> throw new IllegalArgumentException("Unknown type: " + type);
        };
    }
}
```

A factory is useful when creation logic varies or when the caller should depend on an interface rather than concrete classes.

## 31. Strategy design pattern

The Strategy pattern defines a family of interchangeable algorithms behind a common interface. The caller can select a strategy without changing the client code.

```java
interface DiscountStrategy {
    double apply(double amount);
}
class NoDiscount implements DiscountStrategy {
    public double apply(double amount) { return amount; }
}
class TenPercentDiscount implements DiscountStrategy {
    public double apply(double amount) { return amount * 0.90; }
}
class Checkout {
    private final DiscountStrategy strategy;
    Checkout(DiscountStrategy strategy) { this.strategy = strategy; }
    double total(double amount) { return strategy.apply(amount); }
}
```

**Factory vs. Strategy:** A factory focuses on creating the right object. A strategy focuses on selecting and executing interchangeable behaviour. They can be used together.

## 32. Functional vs. non-functional requirements

- **Functional requirements:** What the system must do. Example: “Users can upload a visa document and view its status.”
- **Non-functional requirements:** How well or under what constraints it must work. Examples: performance, availability, scalability, security, accessibility, maintainability, and reliability.

Good non-functional requirements are measurable, such as “95% of API responses complete within 300 ms under 500 concurrent users,” if that target is appropriate for the system.

## 33. What is an agentic workflow?

An agentic workflow uses an AI model to pursue a goal through multiple steps, potentially selecting tools, observing results, and deciding what to do next.

Typical flow:
1. Receive a user goal.
2. Understand the request and plan steps.
3. Call an approved tool/API when needed.
4. Observe the tool result and decide the next step.
5. Validate the result, apply safety/permission checks, and respond.

**LLM chatbot vs. agentic workflow:** A simple chatbot often generates a response from a prompt and context. An agentic system can iteratively plan and invoke tools. Agentic systems need bounded steps, access controls, input/output validation, logging, and human approval for sensitive actions. Do not claim a system is agentic merely because it calls an LLM once.

## 35. Coding: Sort by frequency, then by value

**Input:**

```java
int[] nums = {4, 6, 2, 5, 2, 3, 3, 3};
```

**Expected output:**

```text
[3, 3, 3, 2, 2, 4, 5, 6]
```

**Rule:** Sort by frequency in descending order. If two values have the same frequency, sort those values in ascending order. Here, `3` appears 3 times, `2` appears 2 times, and `4`, `5`, and `6` each appear once.

### Java solution (simple and interview-friendly)

```java
import java.util.*;

public class Main {
    public static int[] sortByFrequency(int[] nums) {
        Map<Integer, Integer> frequency = new HashMap<>();

        for (int num : nums) {
            frequency.put(num, frequency.getOrDefault(num, 0) + 1);
        }

        Integer[] result = Arrays.stream(nums).boxed().toArray(Integer[]::new);

        Arrays.sort(result, (a, b) -> {
            int frequencyCompare = Integer.compare(
                frequency.get(b), frequency.get(a)
            );

            if (frequencyCompare != 0) {
                return frequencyCompare; // higher frequency first
            }

            return Integer.compare(a, b); // tie: smaller value first
        });

        return Arrays.stream(result).mapToInt(Integer::intValue).toArray();
    }

    public static void main(String[] args) {
        int[] nums = {4, 6, 2, 5, 2, 3, 3, 3};
        System.out.println(Arrays.toString(sortByFrequency(nums)));
    }
}
```

**Output:**

```text
[3, 3, 3, 2, 2, 4, 5, 6]
```

### How the code works

1. Build a frequency map: `{2=2, 3=3, 4=1, 5=1, 6=1}`.
2. Box the `int[]` into `Integer[]` because `Arrays.sort` needs an object-array comparator.
3. Compare two values by their frequencies in descending order.
4. If their frequencies are equal, compare the values in ascending order.
5. Convert the sorted `Integer[]` back into `int[]`.

**Complexity:** Frequency counting is `O(n)` on average; sorting is `O(n log n)`. Extra space is `O(n + k)`, where `k` is the number of distinct values.

## Quick revision: important one-line answers

- **Is `HashMap` thread-safe?** No, not for concurrent structural updates without external coordination.
- **Is synchronous code always thread-safe?** No.
- **Can streams be reused?** No; create a fresh stream for each terminal operation.
- **Does `peek()` transform elements?** No; use `map()` for transformation.
- **Is “fail-safe iterator” an official Java term?** No; it is an informal label.
