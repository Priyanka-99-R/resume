## 1. Observable vs Promise

### Promise

A **Promise** represents one asynchronous result.

It has three states:

-   Pending
-   Fulfilled
-   Rejected

A Promise normally gives **one final result**.

``` javascript
const promise = new Promise((resolve, reject) => {
  setTimeout(() => {
    resolve("Data received");
  }, 1000);
});

promise
  .then(data => console.log(data))
  .catch(error => console.log(error));
```

### Observable

An **Observable** can emit **multiple values over time**.

Angular uses **RxJS Observables** heavily for HTTP calls, events,
reactive forms, and streams.

``` typescript
this.http.get<Employee[]>('/api/employees')
  .subscribe(data => {
    console.log(data);
  });
```

### Main difference

  -----------------------------------------------------------------------
  Promise                             Observable
  ----------------------------------- -----------------------------------
  Usually one result                  Can emit multiple results

  Eager once created                  Generally starts when subscribed

  `.then()` / `.catch()`              `.subscribe()`

  Cannot normally cancel the Promise  Subscription can be
  itself                              cancelled/unsubscribed

  Native JavaScript                   RxJS

  Good for one async result           Good for streams/multiple values
  -----------------------------------------------------------------------

### Interview answer

> Promise is mainly used when I expect one asynchronous result, whereas
> Observable is useful when I need a stream of values over time. In
> Angular, HTTP APIs return Observables, and I subscribe to them.
> Observable also supports operators like map, filter, switchMap and
> cancellation through unsubscribe.

# 2. Synchronous vs Asynchronous JavaScript

## Synchronous operation

Synchronous code executes **line by line**. The next statement waits for
the current statement to finish.

``` javascript
console.log("Start");

let a = 10;
let b = 20;

a = a + b;

console.log(a);

console.log("End");
```

Output:

``` text
Start
30
End
```

`a = a + b` is synchronous.

### Important point

`console.log()` itself is synchronous in normal JavaScript execution.

------------------------------------------------------------------------

## Asynchronous operation

An asynchronous operation allows JavaScript to continue executing other
work while waiting for an operation such as:

-   HTTP request
-   Timer
-   File operation
-   Database/network operation

Example:

``` javascript
console.log("Start");

setTimeout(() => {
  console.log("API result");
}, 1000);

console.log("End");
```

Output:

``` text
Start
End
API result
```

# 3. async and await -- Detailed Explanation

`async` and `await` make Promise-based asynchronous code easier to read.

## async

When a function is declared with `async`, it always returns a Promise.

``` javascript
async function getData() {
  return "Hello";
}
```

This is effectively a Promise.

``` javascript
getData().then(result => console.log(result));
```

------------------------------------------------------------------------

## await

`await` waits for a Promise to settle **inside an async function**.

``` javascript
async function getData() {
  const result = await fetch('/api/employees');
  console.log(result);
}
```

Important:

> `await` does not block the entire JavaScript application or browser
> thread. It pauses the execution of that async function and allows
> other JavaScript work to continue.

------------------------------------------------------------------------

## async/await with try/catch

``` javascript
async function getEmployees() {
  try {
    const response = await fetch('/api/employees');

    if (!response.ok) {
      throw new Error("API failed");
    }

    const employees = await response.json();

    console.log(employees);
  } catch (error) {
    console.error(error);
  }
}
```

### Interview answer

> `async` makes a function return a Promise. `await` waits for the
> Promise result inside that async function, making asynchronous code
> look sequential. It does not block the JavaScript event loop; while
> the function is waiting, other work can continue. I normally use
> try-catch around await when I need to handle failures.

------------------------------------------------------------------------

# 4. async/await -- Sequential vs Parallel

## Sequential

``` javascript
const user = await getUser();
const orders = await getOrders();
```

The second operation starts after the first one completes.

## Parallel

If the calls are independent:

``` javascript
const [user, orders] = await Promise.all([
  getUser(),
  getOrders()
]);
```

### Interview point

> If two API calls are independent, I prefer `Promise.all()` so they can
> execute concurrently instead of unnecessarily waiting for one another.

# 5. JWT -- Complete Token Creation and Validation Flow

JWT means **JSON Web Token**.

A JWT commonly has three parts:

``` text
HEADER.PAYLOAD.SIGNATURE
```

Example structure:

``` text
xxxxx.yyyyy.zzzzz
```

------------------------------------------------------------------------

## 5.1 Header

The header contains metadata about the token.

Example:

``` json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

-   `alg` = signing algorithm
-   `typ` = token type

For asymmetric signing, you may see algorithms such as `RS256`.

------------------------------------------------------------------------

## 5.2 Payload

The payload contains claims.

Example:

``` json
{
  "sub": "101",
  "username": "priya",
  "role": "ADMIN",
  "iat": 1759000000,
  "exp": 1759003600
}
```

Common claims:

-   `sub` -- subject/user identifier
-   `iat` -- issued-at time
-   `exp` -- expiration time
-   `iss` -- issuer
-   `aud` -- audience
-   custom claims such as role

### Important security point

The payload is **not encrypted by normal JWT signing**.

It is Base64URL encoded.

Therefore:

> Do not put passwords, secrets, or sensitive information directly in a
> JWT payload.

------------------------------------------------------------------------

# 6. What happens in jwt.io?

When you paste a JWT into a JWT decoder such as jwt.io:

``` text
HEADER.PAYLOAD.SIGNATURE
```

the tool can decode the Base64URL-encoded:

-   Header
-   Payload

It can display the claims in readable JSON.

The signature is different.

If you provide the correct secret/key and algorithm, the signature can
be verified.

### Important interview statement

> jwt.io does not magically decrypt a JWT. The header and payload can be
> decoded because they are Base64URL encoded. Signature verification
> requires the correct signing secret or key.

# 7. JWT Token Creation Flow

Typical Spring Security flow:

``` text
Client
   |
   | username + password
   v
Login API
   |
   v
AuthenticationManager
   |
   v
UserDetailsService
   |
   v
Database
   |
   v
Password verification
   |
   v
JWT Service
   |
   | Header + Payload
   |      +
   | Secret/private key
   v
Signed JWT
   |
   v
Client
```

### Step-by-step

### Step 1 -- Login request

``` http
POST /api/login
Content-Type: application/json

{
  "username": "priya",
  "password": "password"
}
```

### Step 2 -- Backend authenticates

Spring Security checks the credentials.

Typically:

``` java
Authentication authentication =
        authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(
                username,
                password
            )
        );
```

### Step 3 -- Load user

`UserDetailsService` loads the user from the database.

``` java
UserDetails userDetails =
        userDetailsService.loadUserByUsername(username);
```

### Step 4 -- Generate JWT

``` java
String token = jwtService.generateToken(userDetails);
```

Conceptually:

``` text
Header + "." + Payload
        |
        v
HMAC/RSA signing
        |
        v
Signature
```

Final:

``` text
Header.Payload.Signature
```

### Step 5 -- Return token

``` json
{
  "token": "eyJhbGciOiJIUzI1NiJ9..."
}
```

The frontend stores the token according to the application's security
design and sends it with subsequent requests.

# 9. Why Signature Is Important

Suppose the original payload is:

``` json
{
  "username": "priya",
  "role": "USER"
}
```

Someone changes it to:

``` json
{
  "username": "priya",
  "role": "ADMIN"
}
```

The attacker cannot simply change the payload and make it a valid token.

Why?

Because the signature was generated using the original header + payload
and signing key.

After modification:

``` text
New Header + New Payload
        |
        v
Signature no longer matches
```

Therefore validation fails if the signing key is properly protected.

# 10. What if the User Role Is Updated in the Database?

This is an important interview question.

Suppose:

``` text
Old DB role = USER
Old JWT role = USER
```

Then an administrator changes the database:

``` text
DB role = ADMIN
```

### Existing JWT

The already-issued JWT does **not automatically change**.

The token still contains:

``` json
{
  "role": "USER"
}
```

because a JWT is normally self-contained and remains unchanged after
creation.

------------------------------------------------------------------------

## Scenario A -- Authorization trusts the role inside JWT

If the application reads:

``` java
claims.get("role")
```

and uses that directly for authorization, the old token can continue to
represent `USER` until:

-   token expires
-   token is revoked/invalidated
-   a new token is issued

------------------------------------------------------------------------

## Scenario B -- Backend loads current user from DB

The JWT may identify the user:

``` text
sub = 101
```

Then the backend loads the current user/authorities from the database.

In that design, the updated role can be reflected immediately or
according to the application's caching/security strategy.

------------------------------------------------------------------------

## Better interview answer

> Updating the role in the database does not modify an already-issued
> JWT. If the role is stored as a JWT claim, the old token continues to
> contain the old role until it expires or is otherwise invalidated. For
> immediate role changes, the backend can re-load current authorities
> from the database or use a token revocation/versioning strategy. When
> the user logs in again or refreshes the token, the new role can be
> included in the new token.

# 12. @RequestBody vs @RequestParam vs @PathVariable

## @RequestBody

Reads JSON/request body.

Request:

``` http
POST /employees
```

``` json
{
  "name": "Priya",
  "salary": 50000
}
```

Code:

``` java
@PostMapping
public Employee create(
        @RequestBody Employee employee) {
    return service.create(employee);
}
```

------------------------------------------------------------------------

## @RequestParam

Used for query parameters.

Request:

``` text
GET /employees?department=IT
```

Code:

``` java
@GetMapping
public List<Employee> getEmployees(
        @RequestParam String department) {
    return service.getEmployees(department);
}
```

------------------------------------------------------------------------

## @PathVariable

Used when the value is part of the URL path.

``` text
GET /employees/101
```

``` java
@GetMapping("/{id}")
public Employee getEmployee(
        @PathVariable Long id) {
    return service.getEmployee(id);
}
```

### Easy interview comparison

  Annotation        Example            Purpose
  ----------------- ------------------ ---------------------
  `@RequestBody`    JSON body          Request object/data
  `@RequestParam`   `?name=Priya`      Query parameter
  `@PathVariable`   `/employees/101`   URL path value

# 13. @Component, @Service and @Repository

All three are Spring stereotype annotations and are candidates for
component scanning.

## @Component

Generic Spring-managed component.

``` java
@Component
public class EmailUtil {
}
```

Use it when the class does not specifically represent a service or
repository layer.

------------------------------------------------------------------------

## @Service

Used for the business/service layer.

``` java
@Service
public class EmployeeService {
}
```

It communicates the intent:

> This class contains business logic.

------------------------------------------------------------------------

## @Repository

Used for persistence/data-access classes.

``` java
@Repository
public class EmployeeRepository {
}
```

With Spring Data:

``` java
public interface EmployeeRepository
        extends JpaRepository<Employee, Long> {
}
```

`@Repository` also participates in Spring's persistence exception
translation mechanism when applicable.

------------------------------------------------------------------------

# 14. What if I change @Service to @Component?

Example:

``` java
@Service
public class EmployeeService {
}
```

changed to:

``` java
@Component
public class EmployeeService {
}
```

For normal component scanning and dependency injection, Spring can still
create and inject the bean.

The main difference is **semantic clarity**.

``` text
@Service     -> business/service layer
@Component   -> generic Spring component
@Repository  -> persistence layer
```

### Interview answer

> If I replace `@Service` with `@Component`, the class can still become
> a Spring bean if component scanning picks it up. But `@Service`
> clearly communicates that the class belongs to the service/business
> layer, so I prefer the appropriate stereotype annotation.

# 15. Singleton -- What Does It Mean?

A singleton means:

> Only one bean instance is maintained per Spring ApplicationContext for
> the normal singleton scope.

Example:

``` java
@Service
public class EmployeeService {
}
```

By default, Spring beans are singleton scoped.

------------------------------------------------------------------------

# 16. Where Is the Singleton Instance Created?

It is created and managed by the **Spring IoC container /
ApplicationContext**.

Conceptually:

``` text
Spring Application Startup
        |
        v
ApplicationContext
        |
        v
Component Scanning
        |
        v
Bean Definition
        |
        v
Create Bean Instance
        |
        v
Store/manage bean in ApplicationContext
```

The exact timing can depend on configuration and bean scope. Singleton
beans are commonly instantiated during application startup, especially
with the default eager singleton behavior.

### Important distinction

A Spring singleton is not the same as saying the Java class itself can
never have another instance.

It means:

> Spring manages one instance of that bean within a particular
> ApplicationContext.

------------------------------------------------------------------------

# 17. Singleton Code -- Java

## Simple thread-safe Singleton

``` java
public class Singleton {

    private static volatile Singleton instance;

    private Singleton() {
    }

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }

        return instance;
    }
}
```

This is the **double-checked locking** approach.

### Why volatile?

`volatile` helps ensure visibility and prevents problematic instruction
reordering around object publication.

------------------------------------------------------------------------

## Simpler approach -- Enum Singleton

``` java
public enum Singleton {
    INSTANCE;

    public void execute() {
        System.out.println("Executing...");
    }
}
```

Usage:

``` java
Singleton.INSTANCE.execute();
```

# 18. Spring Boot Calling an External Python API Synchronously

Suppose Python exposes:

``` text
GET http://localhost:5000/api/employees
```

Spring Boot needs to call it synchronously.

A modern Spring Boot approach can use `RestClient`.

## DTO

``` java
public record EmployeeDto(
        Long id,
        String name,
        String department
) {
}
```

## Service

``` java
@Service
public class EmployeeService {

    private final RestClient restClient;

    public EmployeeService(RestClient.Builder builder) {
        this.restClient = builder
                .baseUrl("http://localhost:5000")
                .build();
    }

    public List<EmployeeDto> getEmployeeList() {

        return restClient.get()
                .uri("/api/employees")
                .retrieve()
                .body(new ParameterizedTypeReference<List<EmployeeDto>>() {});
    }
}
```

The call is synchronous from the caller's point of view:

``` text
Spring Service
     |
     | HTTP request
     v
Python API
     |
     | response
     v
Spring Service
     |
     v
Controller
```

The Java thread waits for the HTTP response before the method continues.

### Interview answer

> If the requirement is synchronous communication, I can use Spring's
> `RestClient`. The service sends the HTTP request to the Python API and
> waits for the response before returning the result. I would also
> configure connection/read timeouts and proper exception handling in
> production.

# 19. Spring Boot Employee List -- Controller + Service

## Controller

``` java
@RestController
@RequestMapping("/api/employees")
public class EmployeeController {

    private final EmployeeService employeeService;

    public EmployeeController(EmployeeService employeeService) {
        this.employeeService = employeeService;
    }

    @GetMapping
    public List<EmployeeDto> getEmployeeList() {
        return employeeService.getEmployeeList();
    }
}
```

## Service

``` java
@Service
public class EmployeeService {

    private final EmployeeRepository employeeRepository;

    public EmployeeService(EmployeeRepository employeeRepository) {
        this.employeeRepository = employeeRepository;
    }

    public List<EmployeeDto> getEmployeeList() {

        return employeeRepository.findAll()
                .stream()
                .map(employee -> new EmployeeDto(
                        employee.getId(),
                        employee.getName(),
                        employee.getDepartment()
                ))
                .toList();
    }
}
```

## Repository

``` java
@Repository
public interface EmployeeRepository
        extends JpaRepository<Employee, Long> {
}
```

Bad:

``` java

    // lots of business logic

    // database operations

}
```

Better:

``` text

   v
Service
   |
   v
Repository
```

### Interview answer

> while business logic stays in the service layer. This improves
> separation of concerns, testability, and maintainability.

# 22. Common JWT Interview Questions

## Q1. Is JWT encrypted?

> Not by default. A signed JWT provides integrity and authenticity, but
> the payload can normally be decoded. If confidentiality is required,
> encryption or another secure mechanism is needed.

## Q2. Can a user modify the role in JWT?

> They can modify the encoded payload locally, but without the signing
> key they cannot create a valid signature for the modified token.

## Q3. What happens when JWT expires?

> JWT validation fails because the `exp` claim is no longer valid. The
> application can return 401 and the client can use a refresh-token flow
> if one is implemented.

## Q4. Authentication vs authorization?

> Authentication answers "Who are you?" Authorization answers "What are
> you allowed to do?"

## Q5. Where is JWT validated in Spring Security?

> Commonly in a security filter before the request reaches the
> controller. The filter extracts the Bearer token, validates it,
> creates an Authentication object, and places it in the
> SecurityContext.
